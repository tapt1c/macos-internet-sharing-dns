# QuasarLab: собственная Wi-Fi-сеть с DNS-подменой на macOS

### Обход ограничений провайдерского роутера с помощью Internet Sharing, dnsmasq и rtadvd

## Зачем нужен этот гайд?

Некоторые провайдерские роутеры не позволяют вручную задать DNS-сервер, который они выдают подключённым устройствам через DHCP.

Например, в нашем случае использовался **Huawei H155-380 с прошивкой Tele2 3.0.0.1**. В веб-интерфейсе роутера отсутствовала работающая настройка пользовательского DNS для DHCP.

Это создаёт проблему для проектов вроде eQuasar, которым требуется перенаправлять определённые домены на локальный сервер.

Вместо изменения прошивки роутера мы настроим отдельную экспериментальную Wi-Fi-сеть на MacBook.

**Результат:** все устройства в этой сети автоматически получают локальный DNS-сервер, а нужные домены перенаправляются на Mac.

## 1. Что потребуется

- Mac с macOS, поддерживающий Internet Sharing по Wi-Fi.
- Ethernet-подключение Mac к основному роутеру (в том числе через USB-адаптер).
- Установленный Homebrew.
- `dnsmasq` для локального DNS.
- Терминал с доступом к `sudo`.

Схема подключения:

```text
Интернет
   │
   ▼
Провайдерский роутер
   │ Ethernet
   ▼
MacBook
   ├── en8: подключение к роутеру
   ├── bridge100: 192.168.2.1
   │
   ├── dnsmasq: 192.168.2.1:53
   └── Wi-Fi: QuasarLab
           │
           ├── iPhone
           └── Яндекс Станция
```

Названия интерфейсов и IP-адреса у вас могут отличаться. В этом руководстве используется конфигурация, проверенная на конкретном MacBook.

## 2. Настройка Internet Sharing

Откройте:

**Системные настройки → Основные → Общий доступ → Общий интернет (Internet Sharing)**

Настройте:

- **Общее подключение:** Ethernet или USB LAN.
- **Для устройств, использующих:** Wi-Fi.
- **Название Wi-Fi:** `QuasarLab`.
- **Защита:** совместимый с устройствами режим WPA2/WPA3 или WPA2.
- **Пароль:** собственный надёжный пароль.

Включите Internet Sharing.

После этого macOS должна создать отдельную подсеть и автоматически настроить NAT и DHCP.

Проверим интерфейс:

```bash
ifconfig bridge100
```

В нашей конфигурации его IPv4-адрес:

```text
192.168.2.1
```

Подключите телефон к QuasarLab и убедитесь, что он получает адрес вроде `192.168.2.2` и может пользоваться интернетом.

Официальная документация Apple: [Share the internet connection on Mac](https://support.apple.com/en-euro/guide/mac-help/mchlp1540/27/mac/27).

## 3. Установка dnsmasq

Установите пакет:

```bash
brew install dnsmasq
```

Создайте отдельный конфигурационный файл:

```bash
nano ~/dnsmasq-quasarlab.conf
```

Вставьте:

```ini
port=53
listen-address=192.168.2.1
bind-interfaces

no-resolv
server=1.1.1.1

log-queries
log-facility=-

address=/quasar.yandex.net/192.168.2.1
address=/quasar.yandex.ru/192.168.2.1
address=/scbh.yandex.net/192.168.2.1

local=/quasar.yandex.net/
local=/quasar.yandex.ru/
local=/scbh.yandex.net/
```

Здесь `192.168.2.1` — адрес MacBook в экспериментальной сети.

Параметры `address=` подменяют IPv4-адреса выбранных доменов, а `local=` запрещает пересылать другие запросы к этим доменам внешнему DNS. Это важно для обработки запросов AAAA.

Если используете собственные домены, замените домены Яндекса на необходимые вашему проекту.

Запустите dnsmasq:

```bash
sudo "$(brew --prefix)/sbin/dnsmasq" \
  --no-daemon \
  --conf-file="$HOME/dnsmasq-quasarlab.conf"
```

Оставьте это окно терминала открытым.

В другом окне проверьте:

```bash
dig @192.168.2.1 quasar.yandex.net A +short
```

Ожидается:

```text
192.168.2.1
```

Проверка IPv6:

```bash
dig @192.168.2.1 quasar.yandex.net AAAA +short
```

В нашей конфигурации ответ пустой.

Проверьте и обычный DNS:

```bash
dig @192.168.2.1 example.com A +short
```

Должен вернуться реальный публичный IP-адрес.

**Примечание:** не запускайте параллельно другую службу `dnsmasq` на том же адресе и порту. Сам `dnsmasq` в этом руководстве выполняет только DNS-функцию — DHCP остаётся под управлением macOS.

Для устройств, которые получают DNS через DHCPv4 и действительно отправляют запросы на IPv4-адрес Mac, такого запуска DNS на порту 53 может быть достаточно. Не меняйте `rtadvd` заранее: сначала проверьте трафик с помощью `tcpdump` из следующего раздела.

## 4. Неожиданная проблема: iPhone обходит dnsmasq через IPv6

На этом этапе для части устройств настройка может быть уже достаточной. Однако в нашей конфигурации macOS Internet Sharing на iPhone при автоматической настройке DNS было подтверждено другое поведение: iPhone использовал не IPv4-адрес `192.168.2.1`, а IPv6 DNS MacBook:

```text
fe80::bcd0:74ff:feba:d764
```

Этот обход локального `dnsmasq` подтверждён на iPhone, но ещё не проверен на Яндекс Станции. Не следует предполагать такое же поведение у всех устройств.

Проверить трафик конкретного устройства можно командой:

```bash
sudo tcpdump -ni bridge100 'port 53'
```

Если в выводе видны запросы:

```text
IP6 fe80::... > fe80::...53: A? example.net
```

то этот клиент может обходить наш IPv4 `dnsmasq`. Переходите к разделам 5–7 только если захват трафика подтверждает такой обход через IPv6 DNS.

В наблюдении с iPhone macOS Internet Sharing передавал DNS не только через IPv4 DHCP, но и через два механизма IPv6:

1. RDNSS в Router Advertisement.
2. DHCPv6.

Для этого iPhone потребовалось проверить и скорректировать оба механизма. Это не означает, что такие правки нужны другим устройствам.

## 5. Отключаем объявление IPv6 DNS через RDNSS

Выполняйте этот раздел только если `tcpdump` показал обход локального `dnsmasq` через IPv6 DNS. Сначала определите, какой конфигурационный файл использует `rtadvd`:

```bash
ps aux | grep '[r]tadvd'
```

В нашем случае:

```text
rtadvd -c /etc/com.apple.mis.rtadvd.conf -f -s bridge100
```

**Не изменяйте `/etc/rtadvd.conf` вслепую:** в нашей конфигурации он вообще не использовался.

Создайте резервную копию действующего файла:

```bash
sudo cp -p /etc/com.apple.mis.rtadvd.conf \
  /etc/com.apple.mis.rtadvd.conf.backup
```

Откройте:

```bash
sudo nano /etc/com.apple.mis.rtadvd.conf
```

Изначально у нас было:

```text
bridge100:\
    :maxinterval#135:mininterval#45:\
    :raflags#64:rltime#9000:\
    :addr="fdc2:3b01:9828:7f07::":prefixlen#64:pinfoflags#192:\
    :rdnssaddrs#1:\
    :rdnssaddr0="fe80::bcd0:74ff:feba:d764":\
    :mtu#1500
```

Замените строки:

```text
:rdnssaddrs#1:\
:rdnssaddr0="fe80::bcd0:74ff:feba:d764":\
```

на:

```text
:rdnssaddrs#0:\
```

Значение `0` означает, что `rtadvd` не должен включать сведения о DNS-серверах в Router Advertisement.

Это описано в [документации rtadvd.conf](https://manp.gs/mac/5/rtadvd.conf).

## 6. Отключаем рекомендацию использовать DHCPv6

Этот шаг нужен только если после изменения RDNSS захват трафика всё ещё показывает IPv6 DNS в обход локального `dnsmasq`. В нашем случае после отключения RDNSS iPhone всё равно продолжал получать IPv6 DNS.

Мы обнаружили это командой:

```bash
sudo tcpdump -ni bridge100 -vv 'udp port 546 or udp port 547'
```

Пример ответа:

```text
dhcp6 reply (... DNS-server fe80::bcd0:74ff:feba:d764)
```

Причина — флаг `Other Configuration` в Router Advertisement.

В том же файле `/etc/com.apple.mis.rtadvd.conf` замените:

```text
:raflags#64:rltime#9000:\
```

на:

```text
:raflags#0:rltime#9000:\
```

После наших изменений соответствующая часть конфигурации стала выглядеть так:

```text
bridge100:\
    :maxinterval#135:mininterval#45:\
    :raflags#0:rltime#9000:\
    :addr="fdc2:3b01:9828:7f07::":prefixlen#64:pinfoflags#192:\
    :rdnssaddrs#0:\
    :mtu#1500
```

**Не копируйте IPv6-префикс из этого примера в свою конфигурацию.** Сохраните остальные параметры из файла, созданного вашей системой.

Это изменение не останавливает сервер DHCPv6. Оно только убирает из Router Advertisement рекомендацию клиентам запрашивать дополнительную конфигурацию через DHCPv6. Некоторые устройства могут всё равно обращаться к DHCPv6.

## 7. Применяем изменения rtadvd

В проверенной конфигурации мы завершили работающий процесс и запустили новый с изменённым файлом.

Важно: это вмешательство в служебные настройки macOS, не поддерживаемый Apple способ конфигурирования Internet Sharing. Возможен временный сбой IPv6-подключения.

Сначала убедитесь, что работаете с правильным интерфейсом и существует резервная копия.

Затем:

```bash
sudo pkill -TERM -x rtadvd
```

Проверьте, не запустила ли macOS процесс повторно:

```bash
ps aux | grep '[r]tadvd'
```

Если он не запущен, в нашей конфигурации использовалась команда:

```bash
sudo /usr/sbin/rtadvd \
  -c /etc/com.apple.mis.rtadvd.conf \
  -s bridge100
```

Если процесс уже запустился автоматически, не создавайте второй экземпляр.

Проверьте Router Advertisement:

```bash
sudo tcpdump -ni bridge100 -vv 'icmp6 && ip6[40] == 134'
```

В результате мы получили:

```text
Flags [none]
```

При этом в пакете больше не было:

```text
rdnss option (25)
```

IPv6-префикс продолжал объявляться.

> **Предупреждение после перезапуска Internet Sharing.** macOS может пересоздать `/etc/com.apple.mis.rtadvd.conf` со стандартными параметрами, однако ранее вручную запущенный `rtadvd` может остаться работающим со старой конфигурацией в памяти. В тесте файл был перезаписан, но `rtadvd` (PID 14094, запущен в 22:43) продолжал рассылать Router Advertisement с `Flags [none]`, без RDNSS, а iPhone продолжал использовать IPv4 DNS. Поэтому проверяйте фактические RA, а не только файл:
>
> ```bash
> sudo tcpdump -ni bridge100 -vv 'icmp6 && ip6[40] == 134'
> ```
>
> Это наблюдение не следует считать гарантированным для всех версий macOS: после полноценной перезагрузки поведение не проверялось.

## 8. Проверяем, что устройства используют локальный DNS

На каждом проверяемом устройстве выберите автоматическую настройку DNS, отключитесь от QuasarLab и подключитесь снова. Результат на iPhone сам по себе не подтверждает поведение Яндекс Станции.

На MacBook выполните:

```bash
sudo tcpdump -ni bridge100 \
  '(port 53 or port 546 or port 547)'
```

На телефоне откройте обычный сайт.

В нашем случае после изменений запросы выглядели так:

```text
IP 192.168.2.2 > 192.168.2.1.53: AAAA? example.net
IP 192.168.2.2 > 192.168.2.1.53: A? example.net
```

**Это и есть нужный результат:** телефон использует IPv4 DNS MacBook с автоматическими настройками.

После этого можно проверить, что обращения к выбранным доменам действительно появляются в логах `dnsmasq`.

## 9. Подготовка для eQuasar

Если вы используете проект `yandex-station-root`, IP прокси в файле `config.mk` должен соответствовать адресу MacBook в экспериментальной сети:

```makefile
PROXY_IP := 192.168.2.1
STATION_PLATFORM := yandexmini_2
```

IP колонки (`STATION_IP`) и её идентификатор (`STATION_DEVICE_ID`) указываются после подключения реального устройства.

Настроенная DNS-подмена не означает, что root уже получен. Она лишь перенаправляет нужные запросы на локальный сервер. Для HTTPS необходим соответствующий прокси и совместимая прошивка устройства.

## 10. Возможные проблемы

| Проблема | Что проверить |
|---|---|
| Устройство не получает IP | Активен ли Internet Sharing и работает ли `bootpd` |
| Нет интернета | Подключение Ethernet, NAT и доступность внешнего DNS |
| `dnsmasq` не запускается | Не занят ли порт `53` на нужном IPv4-адресе |
| `dig` возвращает настоящий IP | Запущен ли `dnsmasq`, корректны ли `address=` и `local=` |
| `tcpdump` показывает, что клиент использует IPv6 DNS | RDNSS, DHCPv6, кешированные настройки; меняйте `rtadvd` только после подтверждения обхода |
| После перезапуска всё сломалось | macOS могла пересоздать конфигурацию `rtadvd` |
| DNS работает, но HTTPS нет | DNS-подмена не заменяет корректную настройку TLS-прокси |

### Восстановление настроек

Если вы создали резервную копию по инструкции, можно восстановить исходный конфигурационный файл:

```bash
sudo cp -p /etc/com.apple.mis.rtadvd.conf.backup \
  /etc/com.apple.mis.rtadvd.conf
```

Для возврата Internet Sharing в штатное состояние выключите и снова включите общий интернет через системные настройки macOS. При этом macOS обычно пересоздаёт собственные конфигурационные файлы.

Не изменяйте системные файлы без резервной копии.

## 11. Что стоит учитывать

- Это проверено на одном MacBook (MacBook Pro 2021, M1 Pro) с конкретной конфигурацией macOS ( голден гей) ). На других версиях расположение файлов и поведение служб могут отличаться.
- Обход локального `dnsmasq` через IPv6 DNS подтверждён на iPhone при macOS Internet Sharing. На Яндекс Станции он ещё не проверен.
- Настройки `rtadvd` в нашей схеме временные, нужны только при подтверждённом IPv6-обходе и не гарантированно сохраняются после перезапуска Internet Sharing.
- Некоторые клиенты используют собственные DNS-серверы, DoH или DoT и могут обходить локальную подмену.
- Не следует использовать эту конфигурацию для перехвата чужого трафика или на устройствах без разрешения владельца.
- Для постоянной домашней инфраструктуры отдельный роутер с управлением DHCP, DNS и IPv6 RA надёжнее.
